# 指標が何を測っているか

指標の名前だけでは，何を測ったのかは分からない．1 年後に実験を見返したとき，
`mean_n_surviving` は推測であり，`normal.q_ordinal.0.mean` は推測にもならない．
`metrics.csv` の列は `run_uid, step, step_unit, scope, name, value` の 6 つで，
説明を書く場所がどこにもない．

説明は **任意**であり，これからも任意のままである．すでに存在する run に説明は無く，
遡って付けることもできない．必須化の代わりに置いたのが [監査](#監査) である．

## 名前ごとに説明を書く設計が成立しない理由

ある集約リポジトリは **13,589 種類**の指標名を持つ．うち 13,528 件は 2 つの
リポジトリのもので，人が実際に名づけた指標は，残り 5 つのリポジトリを合わせて
**74 件**しかない．

大きいほうは語彙ではなく，直積である．

```
normal.q_ordinal.0.mean
   │       │      │   └ 集約         （mean / max）
   │       │      └ 成分番号
   │       └ 指標系
   └ シナリオ                        （normal / masquerade / …）
```

13,589 件の説明は誰も書けない．そこで宣言は，**1 つの名前**の意味か，
**名前の形**の意味を軸ごとに述べる．4 つの形で 1 万件を超える名前が説明される．

## 宣言

リポジトリは，その直下の `runvault.toml` で指標を宣言する．

```toml
# 名前そのもの．手で名づけた 74 件はこれで足りる．
[metrics."convergence_rate"]
meaning   = "収束した試行の割合"
unit      = "ratio"
direction = "up"
range     = [0.0, 1.0]
scope     = ["run"]

# 名前の形．生成された指標群はこちらで，軸ごとに意味を書く．
[[metric_patterns]]
pattern   = "{scenario}.q_ordinal.{index}.{agg}"
meaning   = "IDES の順序統計量"
unit      = "count"
[metric_patterns.axes]
scenario = "投入した通信シナリオ"
index    = "成分番号"
agg      = "その成分の集約"
```

| 欄 | 意味 |
| --- | --- |
| `meaning` | 何を測っているか．名前の宣言では必須，形の宣言では任意 |
| `unit` | `ratio` / `count` / `sec` / `usd` など |
| `direction` | `up` / `down` / `none`．どちらが良いか |
| `range` | 取りうる範囲（有界なら） |
| `scope` | どの粒度で意味を持つか |

`direction` があると，画面が «2 つの run のどちらが良くなったか» を言える．
**`none` は誰かが選んだ値**であって — «この数は評価ではなく記述である» — 欄を
書かないこと（誰も決めていない）とは別のことを言っている．

`pattern` の中で `{名前}` と書いた区画は軸で，任意の 1 区画に当たる．それ以外の
区画は字面どおり一致しなければならない．**区画の数まで一致する必要がある** —
`a.{x}` は `a.b.c` を説明しない．前方一致にすると，誰も説明していない深い一族を
1 つの形が勝手に取り込む．

名前そのものの宣言は，同じ名前に当たる形より常に優先される．一族をまとめて説明し，
その中の 1 つだけを個別に述べる，という書き方ができる．

## run が持つもの

宣言はリポジトリのものである — 指標の意味は実験の性質であって，その 298 本ある
run のうちの 1 本の性質ではない．しかし run がリポジトリ内のファイルを指すと，
そのファイルが変わった瞬間に古い run の意味が変わり，チェックアウトが移動すれば
失われる．そこで宣言を出どころ，run ディレクトリの `metrics.meta.json` を記録とする．
`config.json` が `parameters` について既に行っている分け方と同じである．

`finish()` がこれを書く．書くのは **当てはまる分だけ**である．

```json
{
  "schema_version": "1.0",
  "metrics": {"convergence_rate": {"meaning": "…", "unit": "ratio", "direction": "up"}},
  "patterns": [{"pattern": "{scenario}.q_ordinal.{index}.{agg}", "meaning": "…", "n_matched": 1270}],
  "undescribed": ["mean_n_surviving"]
}
```

- 指標を 3 つ記録した run は，残る 70 件の説明を持たない．1 つのリポジトリの
  4 つの形を，298 本の run 全部で繰り返すこともしない．
- 何も説明が当たらない名前は，黙って落とさず `undescribed` に **並べる**．
  «誰も書いていない» と «ファイルが欠けている» を読み手が区別できるようにするため．
- 説明が 1 つも当たらないときは **ファイルを書かない**．«何も説明されていない» と
  書いたファイルは，無いファイルと同じことしか言っていない．

`runvault.toml` を持たないリポジトリでも run は記録できる．必須にすると，これは
«追加» ではなく «破壊的変更» になる．

宣言は **run の開始時に 1 度だけ**，リポジトリの直下から読む．`RunOptions::repo_root`
に渡した場所か，それが無ければ `origin = code` のときに git から引いた根である．
走っている最中に編集されたファイルに «その run が何を測ったか» を決めさせない．
どちらも無いときは何も読まない — 作業ディレクトリを勝手に漁らない．

`runvault sync` は `metrics.meta.json` を集約リポジトリまで運び，
`runvault query --refresh` がそれを索引の `metric_docs` 表へ平坦化する．

## 監査

```bash
runvault metrics audit --vault <VAULT>
runvault metrics audit --vault <VAULT> --limit 0 --json
```

数える手段の無い «任意» は «書かれない» と同じなので，監査が実験ごとに，run が
記録した指標名の種類・そのうち説明のあるもの・無いものを数える．

- 宣言された形に当たる名前は **その形に畳む** — 1 行に，形と件数だけ．
  1 万件を並べたものは報告ではなく壁である．
- 残ったものは **名前を出す**．数だけでは直せない．`--limit`（既定 20）で打ち切り，
  打ち切ったときは «N 件のうち M 件を出しています» と書く．`--limit 0` で全件．
- 説明は **名前 → 予約語 → 形** の順に探す．予約指標名の意味はコア語彙のもので
  あってリポジトリのものではないので，区画 1 つの形に `n_units` を横取りさせない．
- 監査は **数えるだけで，何も決めない．** 落とさず，拒まず，
  [`verify`](checks.ja.md) には意図的に含めない．

## ダッシュボードへ渡すもの

`runvault report --obsidian` は説明を `runs[]` ではなく `experiments[]` に載せる．
payload の中の run は，その実験の主要な指標名しか持たないので，そちらに付けると
比べている指標の大半に届かない．

```json
{
  "metric_vocabulary": {"n_units": {"meaning": "…", "scope": ["run"]}},
  "experiments": [
    {"repo_id": "…", "experiment": "…",
     "metric_docs": {"names": {}, "patterns": []}}
  ]
}
```

`metric_docs` は空でも必ず書く．鍵が無いことと空であることは別の主張であり，
画面は «何も説明されていない» と «まだ読めていない» を区別できなければならない．
予約指標の意味は最上位に 1 つだけ置く — その意味は語彙のものであって，実験ごとに
写すと，その実験が宣言したように読めてしまう．

`range` と `scope` は payload へ渡さない．まだどの画面も使っておらず，後から契約に
欄を足すほうが，誰も読まない欄を固定するより安い．

## 条件も同じ

値も名前と同じで，それだけでは何のことか分からない．同じファイルが条件の各設定を
説明する．鍵は JSON ポインタである．

```toml
[parameters."/eps"]
meaning = "信頼幅 ε．これを超えて意見が離れた相手は参照しない"
range   = [0.0, 1.0]

[parameters."/n"]
meaning = "エージェント数"
unit    = "count"
```

裸の名前ではなくポインタなのは，`hash_exclude` と `seed_pointers` が既にポインタで
書かれており，1 つのファイルで «どの設定か» の綴りを 2 つ持ちたくないためである．
ポインタなら入れ子の設定も指せるし，親を指せばその塊ごと説明できる．

`direction` は無い —— 条件は評価ではない．run が **到達した**値が指標で，
**やれと言われた**値が条件である．

`finish()` は当てはまる分を `parameters.meta.json` へ写す．最初のファイルの一節では
なく別ファイルなのは，2 つが独立していて，それぞれ当てはまるものがあるときだけ
書かれるからである．run が持っていて誰も説明していない設定は `undescribed` に並ぶ．
数えるのは最上位だけで，親が説明されていればその下は数えない．

`runvault report --obsidian` は `experiments[].parameter_docs` として渡す．

## Python 実装には無い

Python パッケージは run を書けるが，`runvault.toml` を **読まない**．
`metrics.meta.json` も書かない．Python から記録した run は，数値だけを持ち，
その説明を持たない．これは第 2 実装の欠けであって仕様の違いではない —
形は `schema/v1/metrics.declaration.json` が両方に対して定めている．
