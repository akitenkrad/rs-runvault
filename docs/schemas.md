# Schemas and test vectors

**`schema/v1/` is the specification.** The implementations are held to those
files, not the other way round. Both the Rust reference and the Python second
implementation read them, and CI fails when either drifts.

## The files

| File | Fixes |
| --- | --- |
| `common.json` | The shared definitions — slugs, hashes, timestamps |
| `run.json` | `run.json`: identity, `code`, `env`, `rng`, `llm`, `data`, `lineage`, `research` |
| `config.json` | The config envelope, and the `runvault` control block inside it |
| `metrics.row.json` | A row of `metrics.csv` |
| `reference.row.json` | A row of `reference.csv` |
| `manifest.row.json` | A row of `manifest.csv` |
| `event.json` | A line of `events.jsonl` |
| `status.json` | `status.json` |
| `sync.json` | The receipt left in a synced run directory |
| `vault.config.json` | `runvault-vault.toml`, the aggregation repository's declaration |
| `index.columns.json` | The flattened columns of the seven parquet tables |
| `index.columns.meta.json` | The meta-schema that keeps `index.columns.json` well formed |
| `runs.report.json` | The dashboard payload `runvault report --obsidian` writes |
| `vocabulary.toml` | The core vocabulary, versioned by `vocab_version` |

`vocabulary.toml` fixes the closed value sets — domains, data roles, metric
scopes, step units, event kinds and the reserved metric names. Experiment-specific
terms are namespaced (`x.<repo_id>.<name>`) so they cannot collide with the core
registry. The Python package ships its own copy, because it is installed away
from the repository; `tools/sync_vocabulary.py` copies it across and a test holds
the two byte-identical.

## Test vectors

`schema/v1/testvectors/` holds cross-implementation vectors for the places where
two implementations can silently disagree:

| File | Pins |
| --- | --- |
| `canonicalize.json` | key ordering, NFC, escaping, float formatting, missing vs `null` |
| `length_prefix.json` | the framing that makes a list of inputs unambiguous |
| `hashes.json` | `env_hash` → `config_hash` → `execution_hash`, including the degenerate cases (no data, no code, no locks) |

Every implementation must reproduce **every** field of every case from the inputs
alone. The intermediate `canonical` / `joined` fields exist so that a mismatch
says *where* two implementations diverged, not merely that a hash differs.

**These files are inputs to tests, not generated output.** They are produced by
`tools/gen_testvectors.py`, a second implementation of the canonicalization and
hashing rules written from the specification — and they must never be
regenerated to make a test pass. When the generator and the Rust reference
disagree, one of them is wrong; changing the vectors hides which. Change them
only when the specification changes, and change `schema/v1` first.

The vectors sit deliberately outside `schema/v1/*.json`, which is a non-recursive
glob, so the schema validators do not try to read them as JSON Schemas.

## What CI enforces

Three jobs, and each of them exists to catch a specific way the record could
quietly rot.

**Rust** — `cargo fmt --all --check`, `cargo clippy --all-targets --all-features
-- -D warnings`, `cargo test --all-features`. The `schema-gen` feature emits JSON
Schema from the Rust types so a test can compare them with `schema/v1/*.json`;
that is what stops the Rust structs and the specification from drifting apart.

**Schemas** — `tools/test_schemas.py` pins what the schemas must accept and
reject. Then the vectors are regenerated and `git diff --exit-code
schema/v1/testvectors/` fails on any change: if regenerating from the Python side
alters a byte, someone edited the vectors instead of fixing the implementation.

**Python** — the Pydantic models under `python/src/runvault/models/` are
regenerated by `tools/gen_pydantic.py` and `git diff --exit-code` fails on any
change. The models are a *view* of `schema/v1`, and committing them while
regenerating in CI is what keeps the view from drifting: "it can be generated" is
not the same as "it matches". Then `pytest -q` runs the Python suite.

To run these locally, see [checks](checks.md).
